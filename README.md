# ADS-2 Elasticsearch Demo

Эта ветка - облегченная demo-версия ADS-2 архитектуры для анализа логов.

Здесь больше нет Kafka, Debezium, PostgreSQL как анализируемого источника, Prometheus, Airflow и adcore. Elasticsearch остается внешней базой с логами. Внутри compose поднимается только то, что нужно, чтобы показать идею: LibreChat, ClickHouse, MCP-сервисы, Grafana, Langfuse и служебные базы LibreChat/RAG/Langfuse.

## Что Это За Архитектура

Перед вопросом пользователя логи уже должны быть перенесены из внешнего Elasticsearch в ClickHouse и сжаты в рабочие куски.

Пользователь задает вопрос в LibreChat.

LibreChat передает этот вопрос модели Kimi.

Kimi понимает, что нужно проанализировать логи, и вызывает специальный инструмент для запуска анализа (`ads-log-workflow` MCP).

Этот инструмент создает расследование: сохраняет вопрос пользователя, нужный период времени и область логов, которую надо изучить (`analytics.llm_investigations`).

Затем инструмент составляет список подходящих кусков логов для обработки. Это очередь задач: какие куски уже ждут обработки, какие сейчас обрабатываются, какие готовы, какие упали с ошибкой (`analytics.llm_map_queue`).

ClickHouse сам выбирает нужные заранее сжатые куски логов за указанный период. В этих кусках лежат не сырые огромные логи, а сжатое представление (`analytics.es_log_compressed_batches`).

Для каждого куска ClickHouse делает еще более короткое описание: оставляет важные ошибки, предупреждения, сбои, тайм-ауты и другие подозрительные признаки (`analytics.v_es_log_map_batch_inputs`).

Потом ClickHouse сам вызывает маленький анализ модели по каждому такому куску. Модель не получает все логи целиком, а получает только компактное описание одного куска.

Результат анализа каждого куска сохраняется отдельно. Это кэш: если потом итоговый вывод не получился, уже сделанную работу не надо повторять (`analytics.llm_map_results`).

После этого запускается сведение результатов: ClickHouse берет сохраненные краткие выводы по кускам и собирает из них общий вывод (`analytics.llm_reduce_results`).

Kimi читает уже готовые результаты из ClickHouse: что найдено по кускам, какой общий вывод получился, какой запрос можно выполнить для проверки.

В конце Kimi отвечает пользователю обычным языком, либо дает итоговый запрос, либо помогает построить график в Grafana, если пользователь просил визуализацию.

## Что Внутри Compose

Основные сервисы:

- `librechat` - чат, куда пользователь пишет вопрос.
- `clickhouse` - аналитическая рабочая база ADS-2.
- `elasticsearch-connector` - разово переносит данные из внешнего Elasticsearch в ClickHouse.
- `mcp-log-workflow` - управляет расследованием: создает запись расследования, ставит куски логов в очередь, запускает анализ и итоговое сведение.
- `mcp-clickhouse` - читает схемы, результаты и выполняет проверочные запросы.
- `grafana` и `mcp-grafana` - строят дашборды при необходимости.
- `langfuse-*` - наблюдаемость LLM-вызовов.
- `librechat-db`, `vectordb`, `rag_api` - служебная инфраструктура LibreChat.

Служебный PostgreSQL все еще есть внутри Langfuse и pgvector/RAG. Это не анализируемая внешняя БД, а внутреннее хранилище сервисов.

## Быстрый Старт

1. Подготовьте `.env`:

```bash
cp .env.example .env
```

Минимально укажите:

```bash
KIMI_API_KEY=...
ELASTICSEARCH_PUBLIC_URL=http://localhost:9200
ELASTICSEARCH_BASE_URL=http://host.docker.internal:9200
```

`ELASTICSEARCH_PUBLIC_URL` используется shell-скриптами на вашей машине.
`ELASTICSEARCH_BASE_URL` используется контейнерами внутри Docker.
`ELASTICSEARCH_INDEX_PATTERN` использует маску Elasticsearch, например `nginx-logs-*`.
`ADS_LLM_LOG_INDEX_LIKE` использует ClickHouse `LIKE`, например `nginx-logs-%`.

2. Поднимите demo-стек:

```bash
docker compose up -d
```

3. Загрузите логи из внешнего Elasticsearch в ClickHouse:

```bash
sh tools/elasticsearch-batch-to-clickhouse.sh
```

Если в Elasticsearch еще нет тестовых логов, можно сгенерировать пример логов и залить его во внешний Elasticsearch:

```bash
sh tools/elasticsearch-demo-to-clickhouse.sh
```

4. Сожмите импортированные логи:

```bash
sh tools/compress_raw_logs.sh
```

5. Откройте LibreChat:

```text
http://localhost:3080
```

Спросите, например:

```text
Проанализируй ошибки в nginx-logs за весь доступный период и найди вероятную причину деградации.
```

## Основные Таблицы ClickHouse

- Сырые импортированные логи (`analytics.es_raw_logs`).
- Сжатые пачки логов (`analytics.es_log_compressed_batches`).
- Расследования пользователя (`analytics.llm_investigations`).
- Очередь задач анализа по кускам (`analytics.llm_map_queue`).
- Результаты анализа отдельных пачек (`analytics.llm_map_results`).
- Итоговый общий вывод и возможный проверочный запрос (`analytics.llm_reduce_results`).

## Важная Идея

Kimi не должен тащить в себя миллионы строк логов. Большой объем остается в ClickHouse. Модель получает только короткое описание куска логов, промежуточные выводы и агрегаты. Поэтому demo показывает не просто чат с SQL, а управляемый цикл:

```text
загрузить -> сжать -> проанализировать пачками -> собрать вывод -> проверить SQL/график
```
