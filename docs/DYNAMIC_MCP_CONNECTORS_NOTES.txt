Динамические MCP-коннекторы: журнал решений и изменений
=======================================================

Дата: 2026-05-19
Проект: Agentic-Data-Stack

Цель
----

Модель должна уметь создавать MCP-коннектор под конкретный вопрос пользователя к ClickHouse.

Созданный коннектор должен быть JavaScript-файлом, который можно открыть, прочитать, вручную поправить и переиспользовать.

Где хранятся создаваемые коннекторы
-----------------------------------

Коннекторы больше не хранятся внутри репозитория проекта.

Папка для всех пользовательских MCP-коннекторов:

    /Users/subbotaevgenij/mcp-connectors

Каждый коннектор хранится отдельно от остальных:

    /Users/subbotaevgenij/mcp-connectors/<connector_name>/connector.js

Пример:

    /Users/subbotaevgenij/mcp-connectors/clickhouse_schema_car_inventory_question/connector.js
    /Users/subbotaevgenij/mcp-connectors/clickhouse_data_car_inventory_question/connector.js

Причина такого решения: модель не должна смотреть на старые коннекторы внутри проекта как на готовые примеры и копировать их. Правила создания описываются в prompt, а сами файлы лежат отдельно и доступны для ручного просмотра.

Основная схема работы
---------------------

Для нового нетривиального вопроса к ClickHouse модель должна создать два generated MCP-коннектора.

1. Сначала создается schema discovery connector.

Его задача:

    - сходить в system.tables/system.columns;
    - узнать реальные имена таблиц;
    - узнать реальные имена колонок;
    - вернуть только фактическую структуру БД, подходящую под вопрос пользователя.

2. Потом создается data extraction connector.

Его задача:

    - использовать только найденные на первом шаге таблицы и колонки;
    - валидировать таблицы и колонки через helpers;
    - выполнить SELECT-only запрос;
    - вернуть пользователю данные.

Итоговый ответ модели в чат должен содержать:

    - имя schema-коннектора;
    - путь schema-коннектора;
    - имя data-коннектора;
    - путь data-коннектора;
    - результат из ClickHouse.

Модель не должна выводить исходный код коннектора в чат, если пользователь явно этого не попросил.

Контракт generated-коннектора
-----------------------------

Каждый generated-коннектор должен экспортировать объект такого вида:

    export default {
      name: "clickhouse_some_task",
      description: "Useful human-readable description.",
      inputSchema: {
        type: "object",
        properties: {},
        additionalProperties: false
      },
      async handler({ args, runQuery, helpers }) {
        return [];
      }
    };

Имена generated-коннекторов должны начинаться с:

    clickhouse_

Добавленные MCP tools
---------------------

В MCP server добавлены lifecycle tools для generated-коннекторов:

    list_generated_connectors
    describe_generated_connector
    create_generated_connector
    update_generated_connector
    run_generated_connector

После сохранения коннектор также появляется как обычный MCP tool со своим именем.

Например, пользователь может сказать:

    Используй коннектор clickhouse_data_car_inventory_question

Или:

    Измени коннектор clickhouse_data_car_inventory_question

Что изменено в Docker
---------------------

В docker-compose для mcp-server добавлен bind mount:

    /Users/subbotaevgenij/mcp-connectors:/user-mcp-connectors

Внутри контейнера MCP server пишет generated-коннекторы сюда:

    /user-mcp-connectors

Наружу пользователю показывается путь:

    /Users/subbotaevgenij/mcp-connectors/<connector_name>/connector.js

Что изменено в LibreChat prompt
-------------------------------

LibreChat получает правила:

    - не гадать по памяти;
    - сначала создать schema discovery connector;
    - выполнить schema discovery connector;
    - затем создать data extraction connector;
    - использовать только реальные таблицы и колонки из результата первого коннектора;
    - выполнить data extraction connector;
    - в финальном ответе дать имена коннекторов, пути и результат;
    - не показывать исходный код коннекторов без явной просьбы пользователя.

Также добавлено правило совместимости:

    describe_analytics_table
    sample_analytics_table
    profile_analytics_table
    distinct_analytics_values
    count_analytics_by

должны использовать аргумент:

    table

но MCP server также принимает:

    table_name

Это сделано потому, что модель в LibreChat пыталась вызывать describe_analytics_table с table_name, из-за чего раньше получала ошибку schema validation.

Ограничения безопасности
------------------------

1. Имена generated-коннекторов валидируются.

2. Исходный код generated-коннектора должен:

    - быть непустым;
    - не превышать лимит размера;
    - использовать export default;
    - экспортировать ожидаемое имя коннектора.

3. Коннекторы, которые читают analytics.*, обязаны валидировать используемые колонки до runQuery:

    helpers.analyticsColumnExists
    helpers.analyticsColumns

4. Запрещены опасные паттерны в исходном коде generated-коннектора:

    import
    require(...)
    process
    child_process
    node:
    fs
    eval(...)
    Function(...)
    fetch(...)
    XMLHttpRequest

5. Generated-коннекторы получают read-only helpers:

    runQuery
    analyticsTableExists
    analyticsColumns
    analyticsColumnExists
    boundedLimit
    normalizeFilterOperator
    quoteIdent
    quoteString
    safeSqlIdentifier
    sqlLiteral

6. runQuery по-прежнему разрешает только SELECT-запросы и отсекает мутирующие SQL-операции.

Исправление Grafana dashboards по Prometheus
--------------------------------------------

Prometheus dashboard SQL больше не использует системный now() как якорь временного окна.

Теперь MCP server берет:

    max(sample_time)

из analytics.prometheus_samples или из конкретной метрики, если dashboard строится по одной метрике.

Причина: synthetic Prometheus data может быть исторической. Если строить dashboard от текущего now(), Grafana показывает пустые или красные панели, хотя данные в ClickHouse есть.

Найденные проблемы и исправления
--------------------------------

1. Модель попыталась использовать колонку production_year.

Такой колонки нет в live-схеме ClickHouse. Реальная колонка:

    model_year

После этого усилено правило: generated-коннекторы, которые читают analytics.*, должны валидировать колонки через helpers.analyticsColumnExists или helpers.analyticsColumns перед runQuery.

2. Первый визуальный тест Grafana показал пустые/красные Prometheus panels.

Причина: dashboard SQL использовал now() - INTERVAL ..., а synthetic Prometheus samples были историческими.

Исправление: dashboard time window теперь якорится на max(sample_time) в ClickHouse.

3. LibreChat отправлял describe_analytics_table с аргументом table_name.

Tool schema ожидала table, поэтому запрос падал до выполнения кода.

Исправление: MCP server принимает оба варианта:

    table
    table_name

Важное поведение
----------------

Модель не должна хардкодить текущие demo-таблицы.

Таблицы:

    car_inventory_raw
    prometheus_samples

можно использовать только если schema discovery connector или live schema tool подтвердили, что они существуют и подходят под вопрос пользователя.

Инженерная заметка
------------------

Текущая реализация намеренно поддерживает generated JavaScript files, потому что именно это требуется пользователю.

Для более жесткого production-режима позже можно добавить sandbox или перейти на декларативный DSL. Сейчас безопасность обеспечивается валидацией имени, запретом опасных паттернов, проверкой колонок и SELECT-only выполнением через runQuery.
